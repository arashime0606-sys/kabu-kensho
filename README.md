# 掲載銘柄 全件検証システム

掲載した銘柄について、**結果の良し悪しにかかわらず全件の追跡結果を公開する**ための仕組み。

当てた銘柄だけを後から語ることを、構造的にできなくすることが目的。

---

## 全件性を守る4つの仕組み

1. **除外機構を持たない** — `verify.py` は `picks.json` の全レコードを走査する以外の動作をしない。スキップフラグも除外リストも存在しない。
2. **取得失敗を握り潰さない** — 上場廃止・データ欠損・通信エラーは、すべて `status` として結果に残る。`try/except` で飛ばす経路がない。
3. **人の確認を強制する** — `data_missing` / `error` が1件でもあると `exit 1` になり、GitHub Actions が赤くなる。緑にするには `resolutions.json` に確認結果を追記するしかなく、その追記自体がGitの履歴に残る。
4. **分母を消せない** — レポートには常に「掲載総数 / 評価済」を併記する。

> 生存者バイアスは正面からではなく、エラー処理の裏口から入ってくる。
> 握り潰された銘柄は、たいてい成績の悪い銘柄になる。

---

## リポジトリの前提

**必ず public リポジトリにすること。** この仕組みの価値は「第三者がコミット履歴を検証できる」ことに全面的に依存している。private では改竄していない証明ができず、作る意味がほぼ消える。

副次的な利点として、public なら GitHub Actions の実行時間が無料になる。

将来スクリーニングツールのフロントエンドを足す場合も、**同じリポジトリの `web/` 以下に置く**のがよい。フロントが `data/results.json` を直接読めるので、APIサーバーが不要になる。

```
リポジトリ直下
├── data/          検証データ（このシステム）
├── scripts/       検証スクリプト
├── tests/
├── web/           ← 後で足すフロントエンド（Vercelのroot directoryに指定）
└── .github/
```

## セットアップ

```bash
pip install requests
```

J-Quants API のアカウント（Freeプラン）を作り、**プラン選択まで完了**させてから、ダッシュボードでAPIキーを発行して環境変数に設定する。

```bash
export JQUANTS_API_KEY="発行されたキー"
```

### J-Quants API は V2 のみ

V1 は 2026年6月1日に終了済み。ネット上にはV1前提の記事が大量に残っているので注意する。

| | V1（廃止） | V2（現行） |
|---|---|---|
| 認証 | `Authorization: Bearer` | **`x-api-key` ヘッダー** |
| 株価 | `/v1/prices/daily_quotes` | **`/v2/equities/bars/daily`** |
| 調整後終値 | `AdjustmentClose` | **`AdjC`**（短縮形） |
| 日付 | `YYYY-MM-DD` | `YYYYMMDD`（ハイフン有りも可） |
| 応答 | `{"daily_quotes": [...]}` | `{"data": [...]}` |

V1のエンドポイントを叩くと `HTTP 410` が返る。

GitHub Actions で動かす場合は、リポジトリの Settings → Secrets → Actions に `JQUANTS_API_KEY` を登録する。

## 使い方

### 1. 動作確認（APIに繋がない）

```bash
python scripts/verify.py --mock --latest 2026-05-07
```

擬似データで一通り動く。まずこれで挙動を確認してほしい。

### 2. ロジックのテスト

```bash
python tests/test_core.py
```

上場廃止・判定時点未到来・取得例外のそれぞれで、レコードが消えないことを検査している。

### 3. 実運用の準備

`data/picks.json` の中身はサンプルなので、実運用前に空にする。

```bash
echo '[]' > data/picks.json
```

### 4. 銘柄を掲載する

```bash
python scripts/add_pick.py \
  --code 7203 \
  --name "トヨタ自動車" \
  --rule "PBR1.0倍以下 かつ 配当利回り3.5%以上 かつ 株価1000円以下"
```

追記後は必ずコミットする。**このコミット履歴が、後から書き換えていないことの証拠になる。**

```bash
git add data/picks.json
git commit -m "掲載: 2026-07-30-7203 トヨタ自動車"
git push
```

`picks.json` を手で編集しないこと。既存レコードを壊す事故が起きる。

### 5. 検証する

```bash
python scripts/verify.py
```

`data/results.json` と `REPORT.md` が生成される。

要確認が残っていると `exit 1` になる。その場合は内容を確認して `data/resolutions.json` に追記する。

```json
[
  {
    "id": "2025-02-03-1719",
    "horizon": "*",
    "status": "delisted",
    "resolved_at": "2026-07-30",
    "note": "2025-07-15 TOB成立により上場廃止。判定不能として確定。"
  }
]
```

`horizon` に `"1m"` などを指定すればその判定時点だけ、`"*"` なら全時点に適用される。

---

## 判定のルール

| 項目 | 内容 |
|---|---|
| 判定時点 | 掲載日から 1ヶ月 / 3ヶ月 / 6ヶ月 / 12ヶ月 |
| 使う価格 | **調整後終値（`AdjC`）のみ** |
| 非営業日 | 目標日以降で最初に値がある営業日（10日まで探索） |
| ベンチマーク | TOPIX連動型上場投信(1306) |
| 主要指標 | リターン、ベンチマーク超過リターン、上昇勝率、超過勝率 |

### なぜ調整後終値なのか

1:2 の株式分割があると、素の終値は半分になる。素の終値で比較すると **「50%下落した」と誤判定する**。ここを間違えると全記録が無価値になるので、素の終値は一切使わない設計にしてある。

### なぜベンチマークが必要なのか

地合いが良ければ何を選んでも上がる。「上がった/下がった」だけでは、スクリーニング条件に意味があったかは何も分からない。TOPIX対比の超過リターンで見て初めて意味を持つ。

下落相場で -5% でも、ベンチマークが -10% なら **超過リターンは +5%** になる。

### 判定時点を後から動かさないこと

「まだ上がる可能性がある」と期間を伸ばした瞬間に、記録の価値は消える。`core.py` の `HORIZONS` は固定する。

---

## ステータスの意味

| status | 意味 | ジョブ |
|---|---|---|
| `ok` | 判定できた | 通過 |
| `pending` | 判定時点が未到来。無料プランの12週遅延もここ | 通過 |
| `delisted` | 上場廃止等で判定不能と人が確認済み | 通過 |
| `data_missing` | 価格が取れなかった。**人の確認が必要** | **失敗** |
| `error` | 想定外の例外。**人の確認が必要** | **失敗** |

`delisted` になれるのは `resolutions.json` に確認記録がある場合だけ。黙って消える経路は存在しない。

---

## 無料プランの12週遅延について

J-Quants の無料プランは直近12週間分のデータが取得できない。

つまり **最短の判定サイクルが約3ヶ月**になり、短期の値動きについては原理的に語れない。これは検証の仕組みとしてはむしろ好都合で、短期予測に踏み込まない構造が強制される。

## ファイル構成

```
data/picks.json        掲載記録（追記のみ・書き換え禁止）
data/resolutions.json  人の確認結果（追記のみ）
data/results.json      検証結果（毎回スクリプトが再生成）
REPORT.md              公開用レポート（毎回再生成）

scripts/core.py            判定ロジック（純粋関数・テスト対象）
scripts/jquants_client.py  API接続
scripts/verify.py          実行スクリプト
scripts/add_pick.py        掲載記録の追記

tests/test_core.py     合成データによるロジック検証
tests/test_client.py   APIクライアント（V2仕様）の検証
```

`picks.json` と `resolutions.json` は**追記のみで不変**。
`results.json` と `REPORT.md` は**毎回上書きで再生成**。この分離を崩さないこと。

---

## 注意

本システムが生成するのは過去の記録であり、将来の運用成果を示すものではない。
